# 확장 논의: LFU 전환 · 대규모 병목 · used_memory 모델

현재 구현을 바꾸지 않고, 요구사항이 바뀌거나 규모가 커질 때 어디를 어떻게 고쳐야 하는지
코드 기준으로 정리한다. 수치는 아래 환경에서 직접 측정했다.

- 측정: 2026-09-23, Windows 11, Python 3.12, 단일 프로세스에서 `MiniRedis.execute` 직접 호출
- 측정값은 이 PC 한 번의 실행 결과이며 절대 성능이 아니라 "어디가 튀는지"를 보기 위한 것이다.

## 1. LRU → LFU 전환

### 무엇이 달라지는가

| 항목 | LRU (현재) | LFU |
| --- | --- | --- |
| 퇴출 기준 | 마지막 접근 시각이 가장 오래된 키 | 접근 횟수가 가장 적은 키 |
| 동점 처리 | 없음 (순서가 곧 기준) | 같은 빈도 안에서 LRU로 결정 |
| 접근 시 갱신 | 노드를 맨 앞으로 이동 | 빈도 +1, 다음 빈도 그룹으로 이동 |
| 추가 상태 | 없음 | 키별 빈도, 전체 최소 빈도 `min_freq` |

LRU는 "한 번 대량 조회(스캔)"가 들어오면 자주 쓰던 키가 밀려난다. LFU는 이를 막지만,
과거에 많이 쓰였고 지금은 안 쓰는 키가 오래 남는 문제가 생긴다.

### 자료구조 변경 (O(1) LFU)

정렬이나 힙을 쓰면 접근마다 O(log n)이 든다. 대신 **빈도별 이중 연결 리스트**를 두면
기존 부품만으로 O(1)을 유지할 수 있다.

```text
freq_lists : HashMap  빈도 → DoublyLinkedList (앞 = 최근, 뒤 = 오래됨)
lfu_nodes  : HashMap  키 → (노드, 빈도)          ← 현재 lru_nodes 자리
min_freq   : int      현재 존재하는 가장 작은 빈도
```

| 연산 | 처리 | 비용 |
| --- | --- | --- |
| 새 키 SET | `freq_lists[1].insert_front`, `min_freq = 1` | O(1) |
| GET/SET 성공 | 현재 리스트에서 `remove_node` → `freq_lists[f+1].insert_front`; 옛 리스트가 비었고 `f == min_freq`면 `min_freq += 1` | O(1) |
| 퇴출 | `freq_lists[min_freq].tail` 제거 (같은 빈도 중 가장 오래된 것) | O(1) |
| DEL/만료 | 노드의 빈도 리스트에서 `remove_node` | O(1) |

`min_freq`는 증가만 하고 새 키가 들어오면 1로 돌아가므로 매번 최솟값을 탐색할 필요가 없다.
`DoublyLinkedList`, `HashMap`을 그대로 재사용하므로 새 자료구조는 필요 없다.

### 코드에서 바뀌는 곳

`database.py`에서 LRU를 직접 만지는 곳은 세 군데뿐이다. 정책을 바꿀 때 이 세 곳만 교체한다.

1. `_touch(key)` → 빈도 증가 + 리스트 이동
2. `_set`의 퇴출 루프 `self.lru.tail.data` → `freq_lists[min_freq].tail.data`
3. `_remove_key`의 `self.lru.remove_node(...)` → 해당 빈도 리스트에서 제거

### 정책 설계 시 결정할 것

- **빈도 노화(decay)**: 오래된 인기 키가 영원히 남지 않도록 일정 시간마다 빈도를 절반으로
  줄인다. 실제 Redis는 8비트 로그 카운터 + 분 단위 감쇠(`lfu-decay-time`)를 쓴다.
- **신규 키 보호**: 새 키는 빈도 1이라 바로 퇴출 대상이 된다. Redis처럼 초기값을 5 정도로 주면
  "넣자마자 쫓겨나는" 현상을 줄인다.
- **동점 규칙**: 같은 빈도에서는 LRU(리스트 뒤쪽)로 정한다. 테스트가 결정적으로 나오게 하려면
  이 규칙을 문서에 고정해야 한다.
- **TTL과의 우선순위**: 현재처럼 만료 정리를 먼저 하고, 그래도 초과하면 LFU로 퇴출한다.
  `volatile-lfu`(TTL 있는 키만 후보)를 원하면 후보 리스트를 TTL 유무로 나눠야 한다.
- **호환성**: `CONFIG SET maxmemory-policy allkeys-lru|allkeys-lfu`로 선택하게 하고, 기본값은
  LRU로 두어 기존 테스트와 과제 예시 출력이 바뀌지 않게 한다.

## 2. 대규모(10만 키 이상) 병목과 완화

### 측정 결과

| 측정 | 결과 | 해석 |
| --- | --- | --- |
| SET 10만 회 | 평균 16.9µs, 총 1.69s | 평균은 문제없음 |
| SET 최악 1회 | **361.8ms** (98,304번째 키) | 131,072 × 0.75를 넘는 순간 버킷 262,144개로 리해시 |
| GET 10만 회 | 평균 4.4µs | 해시맵 조회 자체는 빠름 |
| 10만 키 체인 길이 | 최대 3, 빈 버킷 67% | 해시 분포는 양호 |
| KEYS 1회 | 79.8ms | 버킷 26만 개 + 키 10만 개를 모두 순회 |
| 한 키에 EXPIRE를 점점 짧게 10만 번 | **힙 항목 100,000개** | 무효 항목이 루트로 올라오지 않아 남음 |

같은 키에 TTL을 점점 **길게** 다시 설정하면 옛 항목이 먼저 루트에 올라와 바로 버려져 힙이 2개로 유지된다.
문제는 점점 **짧게** 설정할 때만 생긴다.

### 병목 1: 리해시 지연 스파이크

평균은 O(1)이지만 확장 순간 모든 엔트리를 한 번에 옮기므로 그 명령 하나가 수백 ms 멈춘다.
키가 100만 개면 수 초가 된다.

- **점진적 리해시(Redis 방식)**: 옛 테이블과 새 테이블을 동시에 들고, 명령마다 옛 버킷
  몇 개씩만 옮긴다. 조회는 두 테이블을 모두 보고, 삽입은 새 테이블에만 한다.
  총 비용은 같지만 한 명령의 최대 지연이 버킷 몇 개 분량으로 줄어든다.
- **초기 용량 지정**: 키 수를 미리 알면 `HashMap(capacity)`로 시작해 확장 자체를 없앤다.

### 병목 2: 무효 힙 항목 누적

lazy deletion은 무효 항목이 루트에 올라올 때만 버린다. 만료를 계속 줄이는 패턴에서는
힙이 키 수가 아닌 EXPIRE 호출 수만큼 커져 메모리와 O(log h) 비용이 늘어난다.

- **압축(compaction)**: 힙 크기가 유효 TTL 수(`expirations.size()`)의 2배를 넘으면 유효 항목만
  골라 힙을 다시 만든다. O(h)지만 드물게 일어나므로 분할 상환 O(1)이다.
- **인덱스 힙**: 키 → 힙 위치를 저장해 두고 EXPIRE 시 그 자리의 값을 바꾼 뒤
  heapify up/down한다. 키당 항목이 항상 1개로 유지된다.

### 병목 3: 만료 정리가 입력 시에만 일어남

만료는 다음 명령이 들어올 때 정리한다. 명령이 없으면 만료된 키가 메모리에 남아
`used_memory`에 포함되고, 한꺼번에 많이 만료되면 그 순간의 명령 하나가 느려진다.

- **정리 상한**: `_purge_expired`가 한 번에 최대 N개(예: 20개)만 지우고 나머지는 다음 명령으로 넘긴다.
- **주기적 정리**: 입력 대기 중에도 타이머로 조금씩 정리한다. Redis는 초당 10회 무작위 샘플링을 한다.

### 병목 4: KEYS 전체 순회

O(버킷 + 키)라서 키가 늘어나면 선형으로 느려지고 출력량도 커진다.
실제 Redis도 운영 환경에서 `KEYS` 사용을 권장하지 않는다.

- **커서 기반 SCAN**: 버킷 인덱스를 커서로 돌려주고 한 번에 일부 버킷만 반환한다.

### 병목 5: 단일 프로세스 · 단일 스레드

- **샤딩**: 키 해시 % N으로 N개의 `MiniRedis` 인스턴스에 나눠 담는다. 각 샤드가 자기 해시맵,
  LRU, 힙, `maxmemory / N`을 가지므로 리해시와 정리 비용이 1/N로 줄고 병렬 처리가 가능해진다.
  단, LRU는 샤드 단위의 근사가 되고 여러 키를 다루는 명령(KEYS, DBSIZE)은 모든 샤드 결과를 합쳐야 한다.
- **I/O와 실행 분리**: 네트워크를 붙일 경우 Redis처럼 이벤트 루프(비동기 I/O)가 소켓 입출력을
  처리하고 명령 실행은 한 스레드에서 순서대로 한다. 자료구조에 락이 필요 없다는 장점이 유지된다.
- 현재 과제는 CLI 전용이고 동시성은 요구하지 않으므로 이 항목은 설계 방향만 남긴다.

### 우선순위

1. 무효 힙 압축: 코드 몇 줄로 메모리 증가를 막을 수 있다.
2. 정리 상한: 지연 스파이크를 가장 싸게 막는다.
3. 점진적 리해시: 최악 지연을 크게 줄이지만 해시맵 변경 범위가 가장 크다.
4. SCAN, 샤딩: 키 수가 더 커지거나 네트워크 서버로 확장할 때 적용한다.

## 3. used_memory 모델을 바꿀 때

### 현재 모델과 실제 메모리의 차이

```text
used_memory = Σ ( len(utf8(key)) + len(utf8(value)) )
```

키 1만 개(`key:0` ~ `key:9999`, 값 `v0` ~ `v9999`)를 넣고 비교했다.

| 기준 | 값 |
| --- | --- |
| used_memory (과제 공식) | 127,780 바이트 |
| Python 실제 할당 (`tracemalloc`) | 10,993,764 바이트 (약 **86배**) |

차이는 str 객체 헤더, 해시맵 버킷, 체인 노드, `HashMapEntry`, LRU 노드, `lru_nodes` 맵 등에서 생긴다.
즉 현재 `maxmemory`는 "실제 RAM 상한"이 아니라 "데이터 양 상한"이다.

### 오버헤드를 포함하도록 바꾸면 생기는 일

| 영향 | 내용 |
| --- | --- |
| 퇴출 시점 | 같은 `maxmemory`에서 훨씬 일찍 퇴출된다. 과제 예시(`maxmemory 30`)에서는 키 1개도 못 넣는다. |
| 결정성 | `sys.getsizeof`, `tracemalloc` 값은 Python 버전·OS·64비트 여부에 따라 달라 같은 입력에 다른 결과가 나온다. |
| 비교 가능성 | 공식 기준 제출물과 used_memory, evicted_keys 수치를 직접 비교할 수 없다. |
| 비용 | `tracemalloc`은 명령마다 측정하기에 너무 느리다. |

### 권장: 공식 기준은 그대로 두고, 오버헤드는 따로 보고

채점과 테스트가 공식 값에 맞춰져 있으므로 `used_memory` 정의는 **바꾸지 않는다**.
오버헤드를 보고 싶다면 필드를 추가한다.

```text
used_memory:22              ← 과제 공식 (퇴출 판단, 채점 기준)
used_memory_overhead:312    ← 추가 필드, 참고용
maxmemory:30
evicted_keys:1
```

오버헤드를 결정적으로 계산하려면 실제 측정 대신 **고정 상수 모델**을 쓴다.

```text
overhead = 엔트리 수 × ENTRY_COST + 버킷 수 × BUCKET_COST
```

`ENTRY_COST`와 `BUCKET_COST`는 코드 상수로 고정하고 문서에 명시하면 환경과 상관없이 같은 결과가 나온다.

### 퇴출 기준까지 바꿔야 할 때의 보정 방법

정말로 오버헤드까지 퇴출 기준에 넣어야 한다면 다음을 지킨다.

1. **정책 스위치**: `CONFIG SET memory-model payload|overhead`로 선택하게 하고 기본값은 `payload`.
   기존 테스트와 과제 예시는 기본값에서 그대로 통과한다.
2. **기준선(baseline) 보정**: 빈 DB의 고정 비용(초기 버킷 8개 등)을 `baseline`으로 기록하고
   `used_memory - baseline`으로 비교한다. 빈 상태에서 이미 한도를 넘는 문제를 막는다.
3. **한도 환산**: 비교할 때는 `maxmemory`를 같은 모델로 환산한다.
   예: `effective_max = maxmemory × (1 + 평균 오버헤드 비율)`. 같은 데이터 양에서 퇴출 수가 비슷해진다.
4. **테스트 분리**: 공식 모델 테스트는 정확한 값으로 검증하고, 오버헤드 모델 테스트는
   "퇴출 후 한도 이하", "used_memory ≥ 공식 값" 같은 불변식으로 검증한다.
5. **보고 명시**: `INFO memory`에 사용 중인 모델 이름을 함께 출력해 어떤 기준의 숫자인지 드러낸다.
